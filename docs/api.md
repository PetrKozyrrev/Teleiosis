# API (FastAPI)

Интерактивная документация при запущенном сервере: http://127.0.0.1:8000/docs
(доступна только при APP_ENV=dev; staging/prod закрывают docs/OpenAPI).

Состояние на 15.11.2026: готовы материалы, категории, регистрация, вход и выход на сайте, сброс пароля, подтверждение e-mail, смена пароля, настройки пользователя, ограничение частоты запросов, фиксация открытий материала, статистика, напоминания по материалу, отписка от писем. Сайт (папка web/) написан и раздаётся по /app/. Удаление аккаунта и выгрузка данных готовы. Авторизация по e-mail: web-cookie и отдельные mobile Bearer-сессии блока 3 (17.11.2026).

## Авторизация
Пользователь определяется зависимостью `get_current_user` (app/deps.py). Единственный способ входа — e-mail и пароль; на сайте после входа используется HttpOnly cookie (`session` в разработке, `__Host-session` с Secure на боевом сервере; SameSite=Lax, Path=/). Cookie выдаётся при `POST /auth/register` и `POST /auth/login`, удаляется `POST /auth/logout`. В БД хранится только SHA-256-хэш случайного токена.

Изменяющие запросы по cookie и web-auth операции (POST, PUT, PATCH, DELETE) проверяют `Origin`: он должен совпасть с `APP_ORIGIN`; без него допускается `Sec-Fetch-Site: same-origin` или `none`; иначе 403. Для mobile используется Authorization: Bearer с отдельным типом сессии; перенесённая в заголовок web-cookie не подходит. X-Bot-Key/старые Telegram credentials не используются. `POST /auth/telegram` удалён (404).

**Срок сессии:** 14 дней без использования, не больше 60 дней от создания. Успешный запрос продлевает сессию (не чаще раза в сутки). Cookie живёт 60 дней, действительность сессии решает сервер. До 10 активных сессий на пользователя. Формат токена проверяется до обращения к БД (A-Z, a-z, 0-9, _ и -, длина 16-128).

## Ошибки
| Код | Когда |
|---|---|
| 401 | Нет данных входа, они неверные, сессия просрочена или удалена |
| 404 | Чужой или несуществующий ресурс (не 403: чужие данные не раскрываем) |
| 409 | Дубль: категория с таким названием или материал с такой ссылкой уже есть |
| 422 | Некорректные данные запроса (см. также ниже) |
| 403 | Изменяющий запрос по cookie (или регистрация, вход, выход) с чужого или неизвестного origin |
| 429 | Слишком много попыток входа, регистрации или запроса сброса пароля; в заголовке `Retry-After` число секунд до следующей попытки |
| 400 | Недействительный или просроченный токен сброса пароля (причина не уточняется) |

Идентификаторы в адресе вне диапазона BIGINT дают 422.

## Библиотека в мобильном приложении

Клиент использует те же `/contents` и `/categories`, что и сайт. Android/iOS передают мобильный Bearer, а веб-клиент использует cookie и проверку Origin для изменений. Прокси закрытого стенда принимает отдельный заголовок для мобильного транспорта. Список, карточка и записи общие для одного аккаунта. [Конфигурация шлюза](staging.md#мобильная-библиотека-блок-4)

## Поля ответов
- **Пользователь (UserOut):** `id`, `email`, `timezone`, `reminders_enabled`, `reminder_time` (строка `ЧЧ:ММ`), `email_verified_at` (`null`, пока адрес не подтверждён).
- **Категория:** id, name, created_at, contents_count (сколько материалов пользователя в категории).
- **Материал (ContentOut):** `id`, `category_id`, `title`, `url`, `description`, `note`, `content_type`, `source`, `image_url`, `status`, `studied_at`, `created_at`, `updated_at`, `last_opened_at` (null, пока ссылку не открывали), `open_count`.

## POST /contents
- Принимаются только http и https, длина до 2048 символов, без пробелов, хост с точкой, без логина и пароля в ссылке. Адрес без схемы получает `https://`. Недопустимая ссылка даёт 422.
- Ссылка нормализуется для поиска дублей: https, без www, без трекинговых параметров и фрагмента `#`; YouTube приводится к `youtube.com/watch?v=ID`; `t.me` без параметров.
- Дубль среди материалов пользователя: 409 с телом `{"detail": {"message": "Already saved", "existing_id": N}}`.
- Название: из запроса (до 300 символов), иначе загруженное со страницы, иначе временное (адрес без https:// или первая строка заметки). Заметка до 10 000 символов.
- Загрузка метаданных best-effort (до ~6 секунд, при любой ошибке сохраняется ссылка), с защитой от SSRF (app/metadata.py); YouTube через oEmbed. Для заметок без ссылки метаданные не загружаются.
- Источник и тип определяются по адресу: youtube/video, telegram/post, web/article; заметка: other/note.

## GET /contents: параметры
`q` (поиск по названию, до 100 символов), `status` (unseen, planned, studied, irrelevant), `source` (youtube, telegram, web, other), `category_id`, `uncategorized` (true), `sort` (newest, oldest, title), `limit` (1-100, по умолчанию 20), `offset` (до 1 000 000).
`category_id` вместе с `uncategorized` даёт 422. К любой сортировке добавляется id для стабильного порядка.
Ответ: `{items, total, limit, offset}`.

## PATCH /contents/{id}
- Меняются только `title`, `note`, `status`, `category_id`; лишние поля (в том числе `url`, `user_id`) дают 422. Пустое тело даёт 422.
- `title` и `status` не могут быть null. `title` от 1 до 300 символов.
- `category_id: null` снимает категорию; чужая или несуществующая категория даёт 404 (и ничего не меняется).
- `note`: пустая строка или null удаляют заметку, но у материала без ссылки заметку удалить нельзя (422).

## Офлайн-очередь и условное редактирование

- `POST /contents/submissions` принимает тело `POST /contents` и обязательный UUID в `Idempotency-Key`. Для аккаунта и одинакового payload возвращается 201 с тем же идентификатором материала; поля при повторе отражают его актуальное состояние. Дубликат URL получает 409 с `existing_id`. Для изменённого payload возвращается 409 с `detail.code=submission_payload_changed`; для удалённого материала при повторе возвращается 410 с `detail.code=submission_material_deleted`. Ключ и краткая квитанция хранятся до удаления аккаунта.
- В ответах материала поле `version` начинается с 1 и увеличивается при изменениях названия, заметки, категории и статуса. Учёт открытия оригинала версию не меняет.
- `PATCH /contents/{id}/versioned` принимает те же поля и обязательный `If-Match: "1"` с последней полученной версией. Если версия устарела, API возвращает 412 и `detail.code=content_version_changed`. Старый `PATCH /contents/{id}` сохраняет совместимость.
- Оба новых маршрута должны быть доступны для мобильного транспорта в staging Caddy. APK 0.4.0 использует выделенные маршруты, поэтому старый backend не может принять запрос записи без этих гарантий.

## Статусы
Один статус на материал, переходы свободные. `studied_at` ставится при входе в `studied` и очищается при выходе.

## POST /auth/register
- `email` проверяется и приводится к нижнему регистру (так же будет работать вход); некорректный адрес даёт 422. DNS-проверка адреса не выполняется.
- `password`: от 10 до 128 символов, без требований к составу, не обрезается. В БД хранится только хэш Argon2id.
- `consent` должен быть `true`, иначе 422. Сохраняются `consent_at` и `consent_version` (пока `draft-1`, заменить версией текста от юриста).
- Занятый e-mail (без учёта регистра): 409 `{"detail": "Email already registered"}`. Принятый компромисс: ответ позволяет узнать, что адрес зарегистрирован; закрывается ограничением частоты (подшаг 6.4).
- Лишние поля дают 422. Ответ с `Cache-Control: no-store`.
- `timezone` (необязательно): часовой пояс IANA из браузера. Неизвестное значение молча заменяется на UTC, регистрацию не блокирует.

## GET /stats
Ответ: `total`; `by_status` (`unseen`, `planned`, `studied`, `irrelevant`); `studied_share` = studied / (total минус irrelevant), `null`, если знаменатель 0; `with_url` (материалы со ссылкой) и `opened` (из них с хотя бы одним открытием оригинала), `return_share` = opened / with_url (`null`, если ссылок нет); `added_7d`, `studied_7d`; `top_categories` (до 5, по числу материалов, при равенстве по алфавиту; пустые категории не входят: `{id, name, count}`); `days`: 7 элементов `{day, added, studied}` от самого раннего дня к сегодняшнему.
Окно «7 дней» это сегодняшний и шесть предыдущих дней по часовому поясу пользователя (`users.timezone`, при непрочитанном названии UTC); `added_7d` и `studied_7d` это суммы по `days`. `studied` считается по `studied_at`, который очищается при выходе из статуса «Изучено».

## Ограничение частоты запросов
| Действие | Что считается | Лимит | Окно |
|---|---|---|---|
| POST /auth/login | неудачные попытки на пару e-mail и IP | 5 | 15 минут |
| POST /auth/login | неудачные попытки на IP | 30 | 15 минут |
| POST /auth/register | все попытки на IP | 5 | 1 час |
| POST /auth/password-reset/request | все запросы на e-mail | 3 | 1 час |
| POST /auth/password-reset/request | все запросы на IP | 10 | 1 час |
| POST /auth/email-verification/request | все запросы на пользователя | 3 | 1 час |
| POST /auth/email-verification/request | все запросы на IP | 10 | 1 час |
| POST /auth/change-password | неудачные попытки на пользователя | 5 | 15 минут |
| GET /me/export | все запросы на пользователя | 5 | 1 час | 
| POST /auth/change-password и POST /auth/delete-account | неудачные попытки на пользователя (общий счётчик) | 5 | 15 минут |

- Лимит проверяется до обработки пароля. Заблокированный запрос в журнал не пишется и не нагружает сервер хэшированием.
- Успешный вход обнуляет счётчик пары e-mail и IP, но не счётчик IP.
- Ответ 429 одинаков для существующих и несуществующих e-mail (ключ строится от введённой строки).
- Ошибки формата (422) и отказы по Origin (403) попытками не считаются.
- Блокировки аккаунта нет: ограничение действует на пару e-mail и адрес, а не на сам аккаунт.
- IPv6-адреса считаются по сети /64. Адрес берётся из соединения; за прокси его подменяет uvicorn только для доверенных адресов (`--forwarded-allow-ips`).
- Одновременно считаются не больше 4 хэшей паролей, остальные запросы ждут очереди.
- Значения лимитов это константы в `app/ratelimit.py`.

## Сброс пароля
- Письмо отправляется после ответа (фоновая задача), поэтому время ответа не выдаёт, есть ли аккаунт.
- Новый запрос отменяет прежний токен. Токен проверяется и удаляется одной командой БД, два запроса с одним токеном не пройдут оба.
- Неверный, использованный, просроченный и некорректный токены дают одинаковый 400.
- Ошибка проверки пароля (422) токен не тратит.
- Почта: `EMAIL_BACKEND=console` печатает письмо в терминал (только разработка), `smtp` отправляет через сервер (`SMTP_*`). В `APP_ENV=prod` режим console запрещён. Сбой отправки в запрос не попадает и пишется в лог только типом ошибки.

## Напоминания по материалу
Письмо отправляет воркер (`python -m app.worker`), а не API. Отправляется, когда `scheduled_at` наступил, у пользователя включены напоминания (`reminders_enabled`) и подтверждён e-mail. Просроченные напоминания тоже уходят. Если к моменту отправки материал изучен или неактуален, напоминание отменяется без письма. После отправки статус `sent`, повторных попыток нет. 

## Сайт (статические файлы)
`/` перенаправляет на `/app/`. Файлы из папки `web/` отдаются по адресу `/app/` (HTML, CSS, JS, картинки), без авторизации: в них нет секретов. К ответам `/app/*` добавляются заголовки безопасности (CSP, nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY, Cache-Control: no-cache). Сам API и `/docs` этих заголовков не получают.

По сообщению пользователя от 16.11.2026 локальное закрытое тестирование пройдено; серверный деплой и реальная доставка почты ещё не подтверждены. Блок 3 реализован: /mobile/auth выдаёт opaque mobile-токен и сроки без Set-Cookie; общие защищённые ресурсы принимают mobile Bearer либо web-cookie с проверкой client_type. Мобильные анонимные операции не принимают Authorization; namespace отвергает session-cookie/Origin/Sec-Fetch-Site. Смешанные credentials не имеют fallback: 401, а при нарушении cookie-CSRF сохраняется приоритет 403. Все mobile-ответы no-store, validation не возвращает исходные password/token. Точные DTO/маршруты, ссылки, gateway и проверки: [mobile_auth.md](mobile_auth.md). Дальнейшие изменения блоков 5/7 остаются планом.

|---|---|---|
| 3 | Mobile auth namespace `/mobile/auth` (реализован), тип mobile-сессии, opaque-токен и сроки в ответе | Web `/auth` продолжает выдавать cookie; пароли/consent/rate limit едины; mobile-токен не выдаёт Set-Cookie |
| 3 | Бизнес-ресурсы принимают либо mobile Authorization, либо web-cookie | Проверять тип сессии; смешанные credentials и некорректный Authorization дают 401, без fallback; web-CSRF сохраняется |
| 3 | Reset/verify для mobile, общий отзыв web/mobile-сессий, HTTPS-ссылки с web-fallback | Существующие ссылки и веб-формы работают; схемы опубликованы в mobile_auth.md; OS association на устройствах ещё не подтверждена |
| 5 | Серверная идемпотентность создания URL/заметок | Ключ привязан к user/payload; атомарность; старый POST без ключа сохраняет текущий контракт |
| 5 | Версия ресурса и условное изменение | Устаревший mobile PATCH получает конфликт; все записи увеличивают версию; web-поддержка версии внедряется совместимо |
| 7 | Регистрация устройств, настройки каналов и журнал доставок | Существующая почта/отписка сохраняет смысл; push не включается молча |

Точные DTO, ошибки, TTL идемпотентности и представление BIGINT для TypeScript согласуются в начале соответствующего блока. Полная дельта-синхронизация и файловый upload не входят в первый релиз. Архитектурные правила: [architecture.md](architecture.md); порядок: [mobile_plan.md](mobile_plan.md).

## Закрытый staging (временная проверка)

APP_ENV=staging закрывает docs/redoc/OpenAPI так же, как prod. EMAIL_BACKEND=capture сохраняет MIME-письма в приватный том; HTTP API почтовых операций остаётся прежним, но успешный ответ не означает доставку в реальный ящик. Публичного API чтения писем нет. Gateway Basic Auth отделён от cookie-сессии приложения и не передаётся API. Web JSON-схемы сохранены; mobile namespace добавлен отдельно. На /mobile/* gateway проверяет X-Staging-Authorization и сохраняет Bearer, удаляя credentials шлюза перед API. Подробности: [staging.md](staging.md).
