## Принятые границы

- Android и iOS, первый рынок — Россия; интерфейс первого релиза — русский.
- Мобильное ядро: авторизация, библиотека, категории, статусы, заметки, напоминания, прогресс, настройки и управление аккаунтом.
- Ключевой сценарий: получить ссылку/текст через системное «Поделиться», сохранить черновик и надёжно отправить на общий backend.
- Офлайн: загруженная часть библиотеки и очередь новых ссылок/заметок. Правки существующих материалов, категорий и расписаний требуют сети.
- PDF только по ссылке; файлы, скачивание оригинального контента, обучение, ИИ и подписка позже.
- Сайт остаётся на текущем стеке, общая БД и серверные правила сохраняются. Доступ с нескольких устройств не становится платным.
- React Native + TypeScript + Expo development builds; конкретные SDK, минимальные ОС и нативные модули проверяются в блоке 2.
- По сообщению пользователя локальный закрытый тест пройден без критических ошибок. Серверного теста не было; его не считать выполненным.

Архитектура, сессии, очередь, конфликты и уведомления: [architecture.md](architecture.md). Требования MVP и мобильная приёмочная матрица: [requirements.md](requirements.md).

## Сценарии и экраны

| Экран / вход | Основное действие | Обязательные состояния |
|---|---|---|
| Регистрация / вход | E-mail, пароль, согласие, восстановление | Валидация, ошибка входа, 429, нет сети, повторный вход |
| Библиотека | Поиск по названию, фильтры, сортировка, страницы | Загрузка, пусто, ничего не найдено, ошибка, кэш с датой обновления |
| Добавление / share | Подтвердить URL или заметку, выбрать категорию | Локальный черновик, очередь, отправка, дубль, исправление ошибки |
| Материал | Оригинал, заметка, категория, статус, редактирование, удаление | Нет сети, 404, конфликт версии, подтверждение удаления |
| Категории | Создание, переименование, удаление | Дубль имени, чужая/удалённая категория; материалы сохраняются |
| Напоминание в карточке | Назначить, перенести, отменить | Явный пояс, недопустимая дата, отключённый канал |
| Прогресс | Существующие показатели /stats | Пустая библиотека, отсутствие данных, ошибка; без выдуманного времени обучения |
| Настройки | Часовой пояс, каналы, пароль, экспорт, удаление, выход | Системный запрет push, неверный пароль, очередь перед выходом |
| Письмо / уведомление | Открыть подтверждение, сброс или материал | Холодный запуск, просроченный токен, вход, чужой/удалённый материал |

Полноценная отдельная очередь показана в экране добавления/разделе состояния отправки; успешный локальный приём не маскируется сообщением об успехе сервера. Окончательная компоновка и доступность проверяются в блоках 2 и 4 без изменения утверждённого scope.

## Блоки первого релиза

Оценки — человеко-дни одного опытного инженера, включая документацию и необходимые тесты. Не включают ожидание аккаунтов, юриста, закупок или модерации. После блоков 0–2 пересчитать. В каждом блоке сохраняется регресс сайта при изменении общего API.

### Блок 0. Контракт первого релиза — 2–3 дня

- Цель: зафиксировать границы, архитектуру, приёмку и входные зависимости.
- Scope: результаты аудита, ответы пользователя, экраны, сессии, очередь, каналы, реестр ресурсов, документация. Вне scope: код функций, установки, покупка услуг и публикация.
- Зависимости: утверждение плана (получено). Части: README, docs/, локальный other/mobile_context.md; без app/, web/, БД.
- Acceptance: документы согласованы между собой; каждый основной сценарий имеет проверяемый критерий; внешние вопросы имеют статус и условие закрытия. Полное закрытие включает подтверждение ресурсов и каналов из реестра, не только создание файлов.
- Проверки: локальные ссылки, отсутствие ошибок diff/маркировки статусов, сопоставление текущих API с планируемыми. Runtime-тесты для изменения только документации не нужны.
- Риски/снижение: не принять неизвестные бюджет/устройства/магазины за факты; отразить их явно и не запускать зависимые работы.
- Демонстрация: дорожная карта, схема архитектуры и матрица приёмки; отдельное подтверждение пользователя перед блоком 1.

### Блок 1. Серверная среда и воспроизводимые проверки — 5–8 дней

- Цель: подготовить реальный российский стенд для mobile и проверить эксплуатацию.
- Scope: HTTPS, API/worker, SMTP, окружения, backup/restore, egress, CI Python/миграций, runbook. Вне scope: mobile-функции, Kubernetes и масштабирование.
- Зависимости: блок 0 и подтверждённые серверные ресурсы/договорённости по обработке данных. Части: инфраструктура, compose/config, migrations/tests, CI, docs.
- Acceptance: сайт/API работают через HTTPS; реальное письмо доставлено; процессы переживают перезапуск; backup восстановлен в отдельную БД; CI зелёный. Перед внешними пользовательскими данными закрыты юридические условия.
- Тесты: Python suite в изолированной PostgreSQL; миграции с нуля и прежней ревизии; сохранение данных, smoke почты/сайта, восстановление, ограничения сети.
- Риски/снижение: доступность провайдеров, утечки и SSRF; минимальные доступы, реальные проверки из выбранного ДЦ, никаких секретов в отчёте.
- Демонстрация: серверный стенд с работающей почтой и протоколом восстановления.

### Блок 2. Мобильный каркас и платформенные риски — 5–8 дней

- Цель: доказать совместимость сборки, share, хранилища и push SDK на двух ОС.
- Scope: mobile/, TypeScript, навигация, текущая палитра/типографика, development/release-сборки, пробный share и SecureStore, совместимость нативных SDK. Вне scope: продуктовая библиотека, настоящая авторизация и push-доставка.
- Зависимости: блоки 0–1, macOS-сборка и устройства. Части: mobile/, native-конфигурации, CI сборки, docs.
- Acceptance: установка Android/iOS, холодный/обычный share URL/текста, проверенное безопасное хранилище; выбран production-путь iOS extension, закреплены SDK/минимальные ОС и матрица устройств.
- Тесты: сборки, запуск, навигация, отмена/повтор share, совместимость модулей на физических устройствах. Установка в Expo Go не заменяет эти проверки.
- Риски/снижение: экспериментальный входящий expo-sharing, ограничения iOS, версия RN/RuStore; испытать заранее, нативный модуль согласовать при необходимости.
- Демонстрация: устанавливаемый каркас, принимающий тестовый материал.

### Блок 3. Авторизация и сессии — 6–10 дней

- Цель: существующий аккаунт работает на телефоне и сайте.
- Scope: mobile-сессии, регистрация/вход/выход, reset/verify, SecureStore, HTTPS-ссылки с fallback, истечение сессии. Вне scope: social login и обязательная биометрия.
- Зависимости: блоки 1–2. Части: deps/sessions/auth/account/schemas, миграция auth_sessions, мобильные формы.
- Acceptance: web-cookie и mobile-токены не подменяют друг друга; смешанные credentials отклоняются; сроки/отзыв соблюдаются; reset закрывает все сессии; веб-клиент совместим, секретов в логах нет.
- Тесты: оба типа credentials, CSRF, rate limit, несколько устройств, смена/сброс пароля, холодная ссылка из письма, перезапуск/переустановка.
- Риски/снижение: ослабление web-защиты; общий проверенный код паролей/rate limit, отдельная транспортная auth-ветка.
- Демонстрация: регистрация и вход на телефоне в общий с сайтом аккаунт, проверенный отзыв сессий; мобильный экран библиотеки появляется в блоке 4.

### Блок 4. Библиотека онлайн — 10–15 дней

- Цель: перенести основной пользовательский цикл MVP.
- Scope: список/карточка, поиск/фильтры/сортировка/страницы, добавление URL/заметки, категории, статусы, редактирование/удаление, оригинал. Вне scope: офлайн-запись, файлы, ИИ/обучение.
- Зависимости: блок 3. Части: mobile UI/API, /contents и /categories; только необходимые совместимые изменения backend.
- Acceptance: сохранить → найти → изменить → открыть оригинал; сайт показывает изменения, чужие ресурсы недоступны; корректны ошибки/пустые состояния и недоступные метаданные. Автоповторы неидемпотентных POST пока запрещены.
- Тесты: компоненты, API integration/E2E, дубли, валидация, пагинация, длинный текст, клавиатура, увеличение шрифта, TalkBack/VoiceOver.
- Риски/снижение: расхождение правил и устаревшие ответы; серверная валидация, согласованный контракт и отмена/игнорирование старых загрузок.
- Демонстрация: полноценная библиотека онлайн на двух платформах.

### Блок 5. Кэш, очередь и «Поделиться» — 10–16 дней

- Цель: новые материалы не теряются и не дублируются при плохой связи.
- Scope: SQLite, персистентная очередь, серверная идемпотентность, повторы, share URL/текста, черновик до входа, контроль версий при редактировании. Вне scope: полное офлайн-редактирование, скачивание контента, realtime.
- Зависимости: блок 4. Части: mobile storage/extension, API материалов, миграции идемпотентности/версий; при необходимости точечное обновление веб-PATCH.
- Acceptance: один результат для повторов одной операции и потерянного ответа; сохранение очереди после restart; данные аккаунтов не смешиваются; кэш явно ограничен загруженным; устаревший PATCH не перезаписывает молча.
- Тесты: потеря сети до/после commit, одновременные запросы, повтор заметки/URL, kill/restart, 401/409/422/429/5xx, другой payload с тем же ключом, удаление и поздний повтор, смена аккаунта.
- Риски/снижение: потеря/дубли и конфликт сайта с mobile; атомарные записи, owner_id/UUID, фиксированный payload, явные состояния и условное обновление.
- Демонстрация: поделиться без сети, закрыть приложение, открыть и получить один материал на сервере.

### Блок 6. Настройки, прогресс и данные — 5–8 дней

- Цель: завершить соответствие мобильного ядра MVP.
- Scope: расписание/перенос/отмена напоминаний, IANA-пояс, /stats, пароль, экспорт, удаление и очистка устройства. Вне scope: push-доставка и расширенная аналитика.
- Зависимости: блоки 3–5. Части: mobile screens, /me/settings, /stats, reminder/account/export API.
- Acceptance: единые настройки, явный пояс, экспорт средствами ОС без секретов; удаление очищает сервер и локальные хранилища; смена пароля сохраняет только текущую сессию.
- Тесты: DST/пояса и границы даты, неверный пароль, каскады, export, SQLite/SecureStore/App Group cleanup, очередь при выходе.
- Риски/снижение: неверное время и остаточные данные; UTC/IANA, перечень всех хранилищ, E2E удаления.
- Демонстрация: управление аккаунтом и напоминаниями с телефона.

### Блок 7. Push и доставка — 10–15 дней

Решение 19.11.2026: реальная проверка RuStore перенесена пользователем на общее тестирование блока 8. Блок 7 остаётся частично реализованным. Клиентский SDK, переходы и APNs не считаются готовыми. [Задачи и проверки D/R/P](mobile_release_checklist.md).

- Цель: напоминание с сервера возвращает к материалу.
- Scope: устройства, APNs/выбранный Android push, permissions, настройки каналов, журнал/повторы/TTL, переход, инвалидные токены. Вне scope: маркетинг, сложные рекомендации, гарантия секунды и exactly-once.
- Зависимости: блок 6, проверенные SDK/аккаунты, согласованные данные провайдеров. Части: worker/digest/reminders/mailer, устройства/доставки в БД, mobile handlers.
- Acceptance: уведомления обеих ОС в согласованных конфигурациях; отказ permissions не мешает ядру; выход отвязывает устройство; изученный/отменённый материал не отправляется при retry; настройками исключены неожиданные дубли каналов.
- Тесты: permissions, холодный запуск, несколько устройств, token rotation, сбои/повторы провайдера, отмена/статус, простой воркера, РФ-сети и фоновые ограничения.
- Риски/снижение: зависимость от дистрибьютора Android и OS; адаптеры, проверка доступности, TTL/dedup, минимальный payload. На границе провайдера неопределённый результат может дать повтор.
- Демонстрация: реальный серверный push открывает карточку после проверки авторизации.

- Зависимости: блоки 0–7; аккаунты/правила магазинов и юридические условия. Части: mobile/backend CI, инфраструктура, метрики/docs и кабинеты.
- Acceptance: нет открытых критических дефектов/потери данных/нарушения изоляции; пройдена матрица устройств, обновление и восстановление; необходимые материалы приняты магазином. Подготовка публикации и фактическая модерация отмечаются раздельно.
- Тесты: E2E с реальным staging API, регресс сайта, реальные share/push, upgrade с очередью и кэшем, нагрузка/безопасность/доступность.
- Риски/снижение: модерация и аккаунты; проверять заранее, выкатывать постепенно; backend должен обслуживать предыдущую версию приложения. Миграции данных не откатывать вслепую вместе с бинарником.
- Демонстрация: доступный внешним пользователям первый релиз; 2–3 недели пилота плюс ожидание модерации.

Итого блоки 0–8: предварительно 61–95 инженерных дней без внешнего ожидания. Наблюдение пилота не означает непрерывную занятость инженера.

## Дальнейшие блоки (не первый релиз)

### Блок 9. Расширенная библиотека — 12–20 дней

- Цель/scope: теги, коллекции, импорт, расширенный поиск, PDF-файлы. Исключены ИИ и учебные планы.
- Зависимости/части: блок 8, требования к файлам; модели/API/БД, приватное объектное хранилище в РФ, mobile. Расширения web отдельно согласовать.
- Готовность/тесты: права и квоты, корректный импорт/export/delete; MIME/размер, вредоносные файлы, дубли, изоляция и миграции.
- Риски/снижение: безопасность/стоимость файлов — проверка, квоты и приватный доступ.
- Демонстрация: коллекция с тегами и PDF. До исполнения разделить организацию библиотеки и файловое хранение на отдельно принимаемые подблоки.

### Блок 10. Цели и ручной план — 15–25 дней

- Цель/scope: цели, материалы, приоритеты, бюджет времени, переносы, прогресс, рекомендации по правилам. Без генеративного ИИ.
- Зависимости/части: блок 8; новые сущности цели/плана/истории, API/mobile/stats.
- Готовность/тесты: пользователь планирует неделю, переносит/завершает задания и видит воспроизводимый прогресс; даты, повторное завершение, удаление, неизвестная длительность.
- Риски/снижение: неоднозначный прогресс — согласовать примеры; ручная длительность, если автоматическая неизвестна.
- Демонстрация: недельный план из своей библиотеки.

### Блок 11. ИИ-анализ — 20–35 дней

- Цель/scope: доступный текст, резюме/тезисы/вопросы, затем ответы по библиотеке. Без обещания анализа любой ссылки и интервального повторения.
- Зависимости/части: стабильная библиотека, провайдер и юридическая схема; фоновые задачи, API/результаты/поисковый индекс/mobile.
- Готовность/тесты: ссылки на источники, явное отсутствие текста, качество/стоимость/лимиты; набор оценки, tenant isolation, prompt injection, повторные задания.
- Риски/снижение: галлюцинации, расходы, передача данных — ограниченные источники, кэш и квоты.
- Демонстрация: анализ с источниками. Анализ одного материала и помощника по библиотеке исполнять отдельно.

### Блок 12. Закрепление — 15–25 дней

- Цель/scope: выводы, карточки, вопросы, история ответов, интервальное повторение. Без социальных функций.
- Зависимости/части: блок 10; блок 11 только для автогенерации; БД/API/планировщик/mobile.
- Готовность/тесты: повторение и история сохраняются между устройствами; алгоритм, время, повтор ответа, доставка напоминаний.
- Риски/снижение: перегрузка/ошибки расписания — ручное управление, ограниченный пилот.
- Демонстрация: цикл повторения и история результата.

### Блок 13. Коммерческий запуск — 10–20 дней после выбора схемы

- Цель/scope: Free/Premium, серверные права/лимиты, платежи/возвраты/восстановление. Без Plus до проверки спроса.
- Зависимости/части: готовая платная ценность из блоков 9–12, юрформа/договоры/магазины; billing API/таблицы/сервисы/mobile.
- Готовность/тесты: purchase/renew/cancel/refund дают одно согласованное право на всех устройствах; sandbox, дубли/перестановка webhook, сверка.
- Риски/снижение: ограничения РФ и разные правила магазинов — проверить каждый канал перед реализацией; покупки валидирует сервер.
- Демонстрация: платёж открывает работающую Premium-функцию. Цены PDF — гипотезы. Можно начать до завершения всех ИИ-блоков при наличии платной ценности.

## Стратегия проверок и выпуска

- Unit: серверные правила; клиентские преобразования/очередь/версии. Component: формы, ошибки, офлайн-статусы, доступность.
- Integration: настоящий PostgreSQL отдельно от рабочей БД; auth/API/idempotency; миграции и сохранение данных. Не полагаться только на create_all.
- E2E: mobile со staging API и регресс сайта; сетевые сбои и процесс приложения; share/push на физических устройствах.
- CI: Python/миграции с блока 1; JS/typecheck/component и сборки после блока 2; целевые E2E с появления функций. Никаких секретов/реальных ПДн в fixtures, артефактах и логах.
- Сначала внутренние release-сборки, затем внешний пилот, затем постепенный выпуск. Сервер обновляется совместимо с предыдущим клиентом; rollback и выключение проблемной функции документируются до выпуска.
- Метрики: активация, D7/D30, изученные материалы, успешность/ошибки очереди, crash и доставка; определения не подменяют изучение простым открытием ссылки. Новые SDK аналитики не подключать автоматически.

## Переход к следующему блоку

Нужны выполненные acceptance criteria, необходимые проверки, отсутствие критической проблемы данных/безопасности/совместимости, демонстрация и отчёт, затем явное подтверждение пользователя. Отсутствие серверных ресурсов не мешает локальным проверкам блока 1, но не позволяет объявить его полностью завершённым.
