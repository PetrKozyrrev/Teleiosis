# Серверный стенд: подготовка и приёмка блока 1

16.11.2026: основатель подтвердил начало блока 1 и сообщил, что хостинг, бюджет, домен и SMTP пока не выбраны. Конфигурация подготовлена для проверки; публичный сервер не создан. Успешная локальная сборка не означает готовность production.

## Что поставляется

- Dockerfile с фиксированными Python-зависимостями, пользователем 10001 и allowlist контекста сборки. .env, Git, PDF и бэкапы не попадают в образ.
- Отдельный deploy/compose.yml; старый docker-compose.yml для разработки не изменяется. PostgreSQL без host-порта, API/worker без host-порта; наружу только 80/443 Caddy.
- Отдельная несуперпользовательская роль приложения, создаваемая при первом старте пустого PostgreSQL. Администраторская роль используется для backup/restore и не передаётся в API/worker.
- Явная команда миграции, healthcheck API по /ready, restart policy, read-only filesystem API/worker и ограниченные логи. API /health — liveness, /ready — только подключение к БД, не проверка SMTP/схемы/воркера.
- Production отключает /docs, /redoc, /openapi.json в FastAPI; proxy дополнительно закрывает их и /ready. Dev-документация остаётся доступной.
- HTTPS Caddy, HSTS без preload/includeSubDomains, proxy-заголовки принимаются только с IP Caddy. Access log выключен: ссылки отписки могут содержать токен в query. Контейнерные error-логи всё равно нужно контролировать; SQL-параметры engine скрыты.
- Backup/restore scripts, шаблон ежедневного systemd timer, CI с отдельными тестовыми БД и контейнерными проверками. Автодеплоя и загрузки образов во внешний registry нет.

## До развёртывания

Выбрать российский регион, бюджет и провайдера, подтвердить домен/DNS/SMTP и юридическую схему до внешних данных тестеров. Кандидаты и критерии — [infrastructure_options.md](infrastructure_options.md). Начальная инженерная гипотеза: 2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD; проверить нагрузкой, это не измеренная ёмкость продукта. БД и сервисы на одной VM — единая точка отказа, приемлемость для пилота подтверждает основатель.

Потребуются Docker Engine и Compose v2 с --wait, Linux, DNS A на IP сервера, доступные 80/443; AAAA публиковать только после отдельной проверки IPv6 и egress. Открыть SSH только для административных адресов; PostgreSQL/API не публиковать. Обычный INPUT firewall не гарантирует фильтрацию Docker-портов — проверить с внешнего хоста. Docker-доступ эквивалентен административным правам. Ничего из этого в текущей сессии на чужом сервере не применялось.

Выделенные сети 172.30.60.0/24 (edge) и 172.30.61.0/24 (backend) не должны пересекаться с VPN/сетями хоста. При изменении адресов согласованно обновить compose, forwarded-allow-ips и egress-шаблон. Не использовать forwarded-allow-ips='*'. Caddy .60.2, API .60/.61.10, worker .11, migrate .12, PostgreSQL .61.2. Веб-origin выводится из DOMAIN, prod/Secure-cookie/SMTP заданы явно.

Перед живым выпуском записать digest образов Python/PostgreSQL/Caddy и идентификатор сборки, просканировать образ и согласовать обновления. Теги в исходном шаблоне облегчают получение security updates, но сами по себе не фиксируют digest.

## Конфигурация и первый запуск

Пример установки кода на сервере: /srv/teleiosis. Секреты не передавать в чат или коммиты. Выполнять на выделенном стенде после подтверждения ресурсов, не поверх работающей локальной БД.

```sh
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env
```

Заполнить файл локальным редактором: DOMAIN, TLS_EMAIL, разные случайные POSTGRES_PASSWORD и POSTGRES_ADMIN_PASSWORD, DATABASE_URL с host=db, SECRET_KEY не короче 32 символов, SMTP_* по провайдеру. POSTGRES_USER — роль приложения, отличная от teleiosis_admin; POSTGRES_DB — база. URL-encode пароль в DATABASE_URL. Стандартный dotenv поддерживает одинарные кавычки для литеральных `$`/`#`; не выполнять `. deploy/.env` как shell-код. Генерировать длинные URL-safe секреты проще, чем вручную экранировать их. Пример можно валидировать, не выводя значения:

```sh
sh deploy/compose.sh config --quiet
sh deploy/compose.sh build api
sh deploy/compose.sh up -d --wait db
sh deploy/compose.sh run --rm migrate
```

Не использовать `compose config` без --quiet в публичных журналах: развёрнутый YAML содержит секреты. Wrapper принимает абсолютный TELEIOSIS_ENV_FILE, если секреты находятся вне репозитория. Для нескольких стендов задать разные COMPOSE_PROJECT_NAME и непересекающиеся подсети; текущий сетевой шаблон рассчитан на один стенд на хосте.

Init-db создаёт роль только на пустом томе; изменение env не меняет пароль существующей роли и не мигрирует старую БД. При смене паролей нужны отдельные административные действия. Нельзя подключать существующий pgdata к этому шаблону без плана переноса ролей и backup/restore.

До API закрыть egress по следующему разделу. Затем:

```sh
sh deploy/compose.sh up -d --wait api worker
sh deploy/compose.sh run --rm --no-deps proxy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sh deploy/compose.sh up -d proxy
sh deploy/compose.sh ps
```

Caddy получает и обновляет сертификаты автоматически при корректном домене и доступных портах; его /data и /config постоянные. SMTP_SECURITY в prod — starttls или ssl, значение none запрещено. Не запускать публичный proxy с тестовым DOMAIN=example.invalid.

## Ограничения исходящих соединений

Приложению нужны БД:5432, публичные HTTP(S)-источники метаданных, SMTP выбранного провайдера и DNS. Caddy нужны DNS/ACME; PostgreSQL не нужен интернет. Compose internal-сеть БД не заменяет egress firewall для приложения и не закрывает DNS rebinding.

deploy/egress.nft.example — пример отдельной nftables-таблицы для IPv4: разрешён PostgreSQL:5432, запрещены новые соединения приложения в частные/служебные/metadata-диапазоны и на хост, established-ответы proxy продолжают работать. **Не установлен и не подтверждён на реальном хосте.** Файл не меняет INPUT-правила админского доступа и не должен заменять существующий firewall. Перед применением администратор обязан проверить:

1. Совпадение IP/subnet из compose, Docker backend (iptables/nftables), bridge netfilter и прохождение контейнерных пакетов через указанные hooks. Проверить синтаксис `nft -c -f deploy/egress.nft.example`.
2. Провайдерские metadata-адреса и дополнительные защищённые диапазоны; IPv6 не включать, пока не подготовлена равнозначная политика.
3. Доступность Docker DNS: если используется частный DNS/SMTP, добавить только узкое согласованное исключение, а не общий доступ к private ranges.
4. Установку правил до запуска приложения; уже установленные соединения разрешаются conntrack. Перезагрузка хоста/Docker не должна снимать правила.
5. Из сетевого namespace API: соединение с db:5432 проходит, контролируемый публичный HTTPS проходит, private IP и metadata IP недоступны. Использовать собственный тестовый private endpoint, не обращаться к чужим metadata-сервисам для «проверки».

Пример подготовки, не команда автоматического применения: скопировать проверенную таблицу в управляемую конфигурацию firewall выбранного сервера. Изменение host firewall выполняется только после проверки доступа и плана отката. Отсутствие установленной и проверенной egress-политики — незакрытый критерий блока 1.

## Проверка сайта, proxy и почты

С внешней машины проверить HTTP→HTTPS, валидность TLS, /health=200, /app/login.html=200, отсутствие /docs, /redoc, /openapi.json, /ready; HSTS и остальные заголовки. Проверить отсутствие публичных 5432/8000. Регистрация/вход/выход с разрешённого Origin работают, изменяющий запрос с чужим Origin отклоняется. Proxy должен передавать реальный IP для rate limit; произвольный X-Forwarded-For клиента не должен его подменять.

SMTP: подтвердить домен отправителя и DNS по инструкции провайдера (DKIM/SPF/DMARC), лимиты/допуски и тип уведомлений. Создать выделенный аккаунт тестера, проверить reset, verify, индивидуальное напоминание и подборку на реальных ящиках. Фиксировать доставку, папку спама, местное время и отсутствие секретов в логах. Успешный SMTP accept не является подтверждением получения письма. Пользовательские тестовые данные/адреса не сохранять в Git. Сейчас внешний SMTP не выбран и эти проверки не выполнены.

## Backup и восстановление

Запуск от оператора с Docker-доступом, каталог вне репозитория, права 0700:

```sh
mkdir -p /var/lib/teleiosis/backups
chmod 700 /var/lib/teleiosis/backups
sh deploy/backup.sh /var/lib/teleiosis/backups/teleiosis-unique_id.dump
sh deploy/restore-check.sh /var/lib/teleiosis/backups/teleiosis-unique_id.dump teleiosis_restore_test_unique_id
```

Заменить unique_id уникальным идентификатором: в имени restore-БД только a-z/0-9/_. Скрипт намеренно требует новую БД с префиксом teleiosis_restore_test_, отказывается от существующей БД и не удаляет её после проверки. При ошибке незавершённая restore-БД остаётся для диагностики. Применяет pg_restore --single-transaction/--exit-on-error, проверяет ревизию/число пользователей и материалов. Для полноценной приёмки дополнительно сверить ожидаемые данные и бизнес-запросы. Параметр --no-owner означает, что восстановленные таблицы принадлежат администратору: перенос в production и назначение владельца приложению — отдельная операция по плану аварийного восстановления, этот скрипт не делает live restore.

Архив custom-format, без владельцев/ACL; итог не перезаписывается, файл 0600, ошибка оставляет .partial без публикации .dump. Проверка pg_restore --list подтверждает индекс, а не полноту содержимого; нужен restore drill. Архив содержит ПДн и хэши паролей — хранить как секрет, шифровать согласованным средством до передачи в отдельное российское хранилище. Не выкладывать в CI artifacts и не держать единственную копию на той же VM. Копии ролей, env, сертификатов/ключей и настроек хранятся отдельно по ограниченному доступу.

deploy/teleiosis-backup.service и .timer — шаблон ежедневного запуска в 03:00 Europe/Moscow с Persistent=true. Перед установкой проверить путь /srv/teleiosis и права, добавить в каталог systemd и включить таймер административно. В этой сессии таймер не устанавливался. Автоматического удаления архивов нет: согласовать сроки хранения/ротацию с основателем и юристом, мониторить диск. Предварительный RPO ежедневного backup — до 24 часов; RTO измеряется восстановлением, не обещается заранее. Для меньшего RPO потребуется WAL/PITR, вне текущего шаблона.

## Обновление, перезапуск и откат

Перед обновлением сохранить проверенный архив, env и идентификатор предыдущего образа. Остановить worker/API при несовместимой миграции; выполнить migrate явно, затем запустить новый образ и smoke. Автомиграции на старте каждого API-процесса нет. Перезапуск контейнера/хоста возвращает сервисы по restart:unless-stopped; намеренно остановленный контейнер не считается автоматически восстановленным.

Worker не имеет отдельного healthcheck/heartbeat; «running» не доказывает успешный проход. Проверять логи ошибок, отправку контрольного напоминания, удержание advisory lock и наблюдать за возрастом pending. Docker healthcheck API сам по себе не перезапускает unhealthy-процесс: нужны внешний мониторинг и операторский runbook. Доступность /ready не подтверждает наличие нужной схемы, поэтому миграции и smoke обязательны.

Откат бинарника допускается только при совместимой схеме. Не запускать alembic downgrade на рабочей БД автоматически: j1f3a5b7c9d0 не восстанавливает удалённые Telegram-значения. Аварийное восстановление — новая изолированная БД, проверка архива/версии, владельца и прав, затем управляемое переключение DATABASE_URL с остановкой писателей и проверкой SMTP/воркера. Старую БД не уничтожать до приёмки.
