## Проверка APK

Нужны Python3.11+, Java17 и Android Build Tools с поддержкой `zipalign -P 16`. Проверены Build Tools37.0.0. Инструменты `apksigner`, `aapt`, `zipalign` берутся из PATH либо из build-tools в ANDROID_HOME/ANDROID_SDK_ROOT.

```sh
cd mobile
python3 scripts/check_android_apk.py artifacts/teleiosis-0.5.2-android-arm64-preview.apk \
  --report artifacts/teleiosis-0.5.2-android-arm64-preview.apk.report.json
```

`preview-policy.json` закрепляет package, version/versionCode, сертификат, адрес API в JS, ABI, SDK и запрещённые разрешения. При подготовке новой версии обновить package.json, app.config.ts и policy согласованно. Включение push потребует отдельного пересмотра permission-политики. Нельзя менять ожидаемый сертификат только ради прохождения проверки. Это политика тестового APK, не подписи магазина.

`scripts/build-android-preview.sh` теперь запускает verifier после копирования APK. При ошибке сборочная команда завершается с ненулевым кодом. Принимать APK можно только с успешным отчётом и совпадающим SHA-256. В CI загрузка APK/отчёта выполняется после успешной сборки и проверки. Локальный файл, оставшийся после неуспешной команды, не считается принятым.

Отдельная проверка verifier без Android-инструментов проверяет синтетические ZIP/ELF и метаданные, без подмены реальной проверки подписи.

```sh
python3 -m unittest discover -s tests -p test_android_artifact.py
```

## Повторение локального замера

Создать отдельную пустую PostgreSQL-БД с именем `teleiosis_pilot_test_<идентификатор>`, настроить DATABASE_URL на неё в приватном окружении процесса. APP_ENV должен быть dev, EMAIL_BACKEND console, PUSH_ENABLED false. Рабочую БД не использовать. Секреты в команды и отчёт не подставлять.

```sh
python -m alembic upgrade head
python scripts/benchmark_library.py --report /tmp/teleiosis-pilot-report.json
```

Скрипт отказывается от другого имени БД/режима или БД с существующими аккаунтами, сам запускает loopback API на свободном порту. HTTP origin не принимает. Созданные вымышленные аккаунты удаляются в finally, schema и БД сохраняются. При принудительном завершении процесса finally может не выполниться, такую БД нужно оставить изолированной и пересоздать для следующего прогона. Живой worker в этой БД не запускать.

CI создаёт отдельную БД, применяет миграцию и сохраняет обезличенный JSON замера. Отчёт содержит агрегаты, без почты, Bearer и текста ответов. Изменения workflow проверены локально по соответствующим командам. GitHub Actions пока не запускался, коммит/push не выполнялись.

## Порядок выпуска и отката

1. Закрыть замечания зависимостей, необходимые D/R/P-задачи из общего протокола и устройство/сеть тестирования. Если часть функции отключена в кандидате, отдельно согласовать состав выпуска. Сохранить commit и состав рабочего дерева, версии инструментов, SHA артефакта и результаты. Подготовленный код блока 7 сейчас ещё в рабочем дереве.
2. Выбрать окончательный package и схему production signing до первого магазина. Существующий debug key служит только тестовым обновлениям. Не использовать его для production. Ключ и резервную копию хранит владелец вне Git. Создание ключа и переключение package/подписи в этом проходе не выполнялись.
3. Собрать проверяемый артефакт, выполнить регрессию обновления с очередью/кэшем на S25. Для iOS отдельно выполнить нативную сборку, подпись, extension/App Group и реальный iPhone-прогон. Пересборка из одинакового lockfile сама по себе не доказывает идентичность бинарников.
4. До согласованного обновления сервера проверить backup/restore и совместимость с APK0.5.1. Подготовить образы прежней/новой API и worker, ревизию миграции, конфигурацию шлюза и процедуру smoke. Фактическое развёртывание согласовать отдельно. Для блока 7 требуется обновить и API, и worker.
5. После rollout повторить HTTPS, web-cookie/CSRF, два аккаунта, очередь, version conflict, export и актуальные push-сценарии. Записать принятые ограничения. Отдельно согласовать карточку магазина, модерацию, публикацию и состав пилота.
6. При дефекте остановить расширение пилота. Push можно отключить флагом и перезапустить согласованные процессы. Откат API/worker выполняется на совместимые прежние образы при сохранении схемы и данных. Downgrade миграции с удалением таблиц не запускать автоматически.
7. Откат клиентского поведения предпочтительно выпускать исправлением с большим versionCode и совместимым хранилищем. Установка старого APK поверх нового может быть запрещена Android. Удаление приложения ради downgrade уничтожает очередь/кэш и не является безопасной процедурой отката. Путь восстановления пользовательских данных сначала проверить на вымышленном аккаунте.

Для диагностики использовать версию/code/SHA, устройство и ОС, время/пояс, шаги, состояние сети и обезличенный статус/тип ошибки. Не запрашивать у тестеров пароли, session/device tokens, содержимое SecureStore/SQLite или полный файл экспорта. Технические журналы перед передачей проверяются на чувствительные данные. Внешний сбор аналитики и crash reporting не подключён.
